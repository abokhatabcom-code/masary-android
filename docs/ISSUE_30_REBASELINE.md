# تقرير إعادة خط الأساس — GitHub Issue #30

**تاريخ المراجعة:** 2026-07-22  
**الفرع:** `official/phase-01-rebaseline`  
**نقطة الأساس:** `85fb471`  
**نطاق المراجعة:** حالة الملفات المتتبعة في المستودع فقط. لم تتضمن المراجعة نشرًا، أو اتصالًا بقاعدة بيانات الإنتاج، أو تغييرًا في Hostinger أو Push V2 أو PWA.

## الملخص التنفيذي

المستودع ليس مشروعًا فارغًا: توجد بنية Android متعددة التطبيقات والوحدات، وتطبيق الطالب يملك مسارًا فعليًا للمصادقة والجلسة والصفحة الرئيسية عبر API أصلي. في المقابل، تطبيقا الإدارة ونقاط البيع ما زالا غلافين بصريين فقط، ولا توجد ميزات أعمال لهما. كما توجد حزمة API خاصة بـ Hostinger ومخطط مصادقة، لكنها **ملفات مصدر/حزمة نشر فقط**؛ وجودها في Git لا يثبت أنها منشورة أو متوافقة حاليًا مع بيئة الإنتاج.

تُعد هذه الوثيقة جردًا وإعادة خط أساس، لا شهادة جاهزية للإنتاج. لا تضيف بيانات افتراضية ولا تغيّر أي سلوك تشغيلي.

## 1. التطبيقات والوحدات الموجودة حاليًا

يعرّف `settings.gradle.kts` عشرة مشاريع Gradle:

| النوع | الوحدة | الحالة المختصرة |
|---|---|---|
| تطبيق | `app-student` | تطبيق فعلي يربط المصادقة والجلسة والصفحة الرئيسية للطالب. |
| تطبيق | `app-admin` | Launcher وواجهة Compose تعرض اسم التطبيق فقط. |
| تطبيق | `app-pos` | Launcher وواجهة Compose تعرض اسم التطبيق فقط. |
| أساسية | `core-ui` | هوية بصرية وثيم Compose مشترك. |
| أساسية | `core-models` | نماذج المصادقة والطالب والجلسة. |
| أساسية | `core-network` | Retrofit/OkHttp وواجهات Auth وStudent Home، والوجهة الافتراضية `https://masary.app/`. |
| أساسية | `core-security` | تخزين الرموز باستخدام Android Keystore، مع مخزن ذاكرة للاختبارات فقط. |
| أساسية | `core-datastore` | حفظ بيانات تعريف الجلسة وربطها بمخزن الرموز الآمن. |
| ميزة | `feature-auth` | واجهة الدخول، ViewModel، مستودع شبكي، استعادة الجلسة وتسجيل الخروج. |

وتوجد، خارج مشاريع Gradle، حزمة `server-hostinger` وتضم PHP API، ملف `.htaccess`، ومخطط MySQL لجداول جلسات المصادقة. هذه الحزمة تعتمد على ملفات وجداول من المنصة الحالية وليست خادمًا مستقلًا مكتملًا داخل هذا المستودع.

## 2. ما تم تنفيذه فعليًا

### Android والبنية المشتركة

- إعداد Android/Kotlin/Compose متعدد الوحدات، بثلاثة application IDs مستقلة، و`minSdk 26` و`targetSdk 35` وJava 17.
- ثيم وهوية مرئية عربية مشتركة، مع دعم RTL وواجهات Material 3.
- إعداد توقيع اختياري موحّد عبر متغيرات البيئة، من دون حفظ keystore أو كلمات مرور في Git.
- تطبيق الطالب يكوّن `DataStoreSessionManager` و`TokenStore` والمستودعات الفعلية عند التشغيل، ثم يقرر بين تسجيل الدخول والمحتوى الموثّق.

### الطالب والمصادقة

- تسجيل دخول الطالب عبر `POST /api/v1/auth/student/login`، مع حالات التحميل والخطأ والتحقق الأساسي من المدخلات.
- حفظ بيانات الطالب غير السرية في Preferences DataStore، وحفظ Access/Refresh tokens عبر Android Keystore.
- استعادة الجلسة، طلب `/api/v1/me`، تحديث الرموز عبر `/api/v1/auth/refresh`، وتسجيل الخروج.
- واجهة رئيسية أصلية للطالب تجلب `/api/v1/student/home` وتعرض بيانات الملف والتقدم والنشاط والاشتراك والمتابعة والموجّه الدراسي وفق الاستجابة الحقيقية؛ لا توجد بيانات طالب وهمية في مسار التشغيل.

### API الموجود في المستودع

- نقاط health، login، refresh، logout، me، وstudent home.
- رموز opaque، وتخزين hash، وتدوير Refresh Token، وكشف إعادة الاستخدام، وحد للجلسات، وrate limiting.
- تجميع بيانات الصفحة الرئيسية في طلب قراءة واحد، مع الاعتماد على وظائف المنصة القديمة إن كانت موجودة.
- مخطط SQL لإضافة جداول وفهارس مصادقة الـ API. لم يُطبّق هذا التقرير المخطط على أي قاعدة بيانات.

### الاختبارات الموجودة

توجد سبعة ملفات لاختبارات JVM تغطي: DataStore session manager، تحويل DTO للمصادقة، مخزن الرموز داخل الذاكرة، مستودع المصادقة، LoginViewModel، تحديث جلسة مستودع الصفحة الرئيسية، وتحويل بيانات الصفحة الرئيسية إلى حالة عرض. لا توجد اختبارات instrumented/device أو اختبارات PHP تكاملية أو اختبارات لتطبيقي الإدارة وPOS.

| حزمة `server-hostinger` | مرشح نشر غير متحقق | المصدر موجود، لكن لم يُنشر ولم يُختبر مقابل إنتاج ضمن هذه المراجعة. |

## 4. الفجوات مقارنة بالوثيقة الرسمية/متطلبات Issue #30

### فجوات مؤكدة من حالة المستودع

1. **الإدارة وPOS غير منفذين وظيفيًا:** وجود APK قابل للبناء لا يعني وجود تطبيق مكتمل.
2. **نطاق الطالب محدود:** الموجود حاليًا هو المصادقة والصفحة الرئيسية؛ لا تظهر وحدات مستقلة للمحتوى الدراسي، الاختبارات، الإشعارات، الملف الشخصي، الاشتراكات، أو إعدادات الحساب.
3. **لا توجد طبقة تنقل عامة واضحة:** الانتقال الحالي شرطي بين Auth وHome، وليس خريطة تنقل قابلة للتوسع.
4. **الاعتماد على production URL افتراضيًا:** لا توجد flavors أو بيئة staging موثقة تفصل الاختبار عن `masary.app`.
5. **عقد API غير موثق آليًا:** لا OpenAPI/schema ولا contract tests بين DTOs وPHP.
6. **API مرتبط بالمنصة القديمة:** يعتمد على ملفات PHP وجداول خارج المستودع، لذا لا يمكن إعادة إنتاج اختبار تكاملي كامل محليًا من هذا المستودع وحده.
7. **تغطية الاختبار جزئية:** لا اختبارات جهاز/واجهة فعلية، ولا اختبارات لتطبيقي الإدارة وPOS، ولا اختبارات أمن/تحميل أو تكامل PHP مع قاعدة معزولة.
8. **Gradle Wrapper غير مكتمل محليًا:** `gradle-wrapper.jar` غير موجود، لذلك `./gradlew` يفشل قبل بدء Gradle. سير Android CI يعوّض ذلك حاليًا بتثبيت Gradle ثم توليد wrapper أثناء المهمة، لكنه لا يصلح تجربة clone المحلية.
9. **توثيق README مختصر:** يشرح البناء والتوقيع فقط ولا يعرّف حدود المنتج، ملكية الوحدات، البيئات، أو سياسة الإصدارات.
10. **لا توجد أدلة جاهزية إنتاج:** لا يمكن استنتاج حالة النشر، توافق schema، الأسرار، الصحة الفعلية، أو جودة البيانات من المصدر وحده، ولم تُفحص الإنتاج التزامًا بقيود المهمة.

### حدود المطابقة

هذه المطابقة مبنية على متطلبات Issue #30 الواردة مع مهمة إعادة خط الأساس وعلى الملفات المتاحة في checkout. لا ينبغي تحويل أي بند غير موجود في المستودع إلى افتراض أو بيانات مصطنعة. عند اعتماد وثيقة منتج تفصيلية إضافية، يجب ربط كل متطلب فيها بوحدة/اختبار/حالة (`منفذ`، `جزئي`، `غير منفذ`) في متابعة مستقلة قبل بدء التوسع البرمجي.

## 5. حالة البناء والاختبارات وGitHub Actions

### نتائج هذه المراجعة

| الفحص | النتيجة | الملاحظة |
|---|---|---|
| `./gradlew test :app-student:assembleDebug :app-admin:assembleDebug :app-pos:assembleDebug` | تعذر التشغيل | فشل فورًا لأن `gradle/wrapper/gradle-wrapper.jar` غير موجود. |

| `find server-hostinger -type f -name '*.php' -print0 \| xargs -0 -n1 php -l` | ناجح | اجتازت ملفات PHP الاثنا عشر فحص الصياغة باستخدام PHP 8.4.22-dev. |

### قراءة ثابتة لـ GitHub Actions

- `android.yml`: يعمل على pull requests وعلى push إلى `main`، ويستخدم Java 17 وGradle 8.11.1، ويولد wrapper، ثم يشغّل اختبار وحدة الطالب ويبني APKs الثلاثة ويرفعها منفصلة.
- المهمة اليدوية في `android.yml` تبني APKs Debug موقعة بعد التحقق من الأسرار، وتحذف keystore المؤقت دائمًا.
- `bootstrap-signing.yml`: يدوي فقط، ويولد keystore وملفات الأسرار كـ artifact خاص لمدة يوم ثم يحذف النسخة المؤقتة من runner.
- `server-api.yml`: يفحص صياغة PHP والمواد الخاصة، ويبني **artifact للتنزيل فقط** عند تغير حزمة الخادم؛ لا يحتوي خطوة نشر إلى Hostinger.
- لا تتوفر من checkout المحلي نتيجة آخر تشغيل فعلي لـ GitHub Actions؛ ما سبق تقييم لتعريفات workflow وليس ادعاءً بأنها خضراء على GitHub.

## 6. الترتيب المقترح لأول المهام البرمجية

1. **إصلاح قابلية إعادة البناء:** استعادة/اعتماد Gradle Wrapper الموثوق، وتوحيد نسخة Gradle بين wrapper وCI، ثم إثبات clean build على Java 17 وSDK 35.
2. **إنشاء بوابة جودة أساسية:** تشغيل كل اختبارات الوحدات في CI، إضافة lint، التحقق من Debug builds الثلاثة، ونشر تقارير الاختبار عند الفشل.
3. **تثبيت عقد الطالب/API:** توثيق schema للاستجابات والأخطاء، إضافة contract tests، وفصل عناوين `dev/staging/production` دون الاتصال بالإنتاج أثناء الاختبار.
4. **تقوية جلسة الطالب:** اختبارات انتهاء/تدوير الرموز والتزامن والخروج، واختبارات instrumented للتحقق من DataStore/Keystore ودورة حياة التطبيق.
5. **تأسيس navigation وواجهات الحالات المشتركة:** قبل إضافة شاشات جديدة، مع الحفاظ على الهوية الحالية وعدم حذف العمل السابق.
6. **استكمال نطاق الطالب حسب أولوية الوثيقة الرسمية:** كل vertical slice يجب أن يستخدم بيانات API حقيقية بعقد موثق؛ لا fixtures في production ولا بيانات وهمية.
7. **تحديد متطلبات الإدارة وPOS رسميًا قبل التنفيذ:** ثم بناء المصادقة والصلاحيات والتنقل لكل تطبيق تدريجيًا، بدل اعتبار shell الحالي منتجًا.
8. **تأهيل API في بيئة معزولة فقط:** اختبارات تكامل وأمن وتحميل مع قاعدة اختبار ونسخة من dependencies القديمة؛ لا تعديل أو migration على الإنتاج من CI أو من مهام التطوير.
9. **مراجعة تشغيلية منفصلة قبل أي نشر:** checklist للنسخ الاحتياطي، rollback، الأسرار، المراقبة، وموافقة بشرية. يبقى النشر خارج هذا الفرع وPR.

## ضوابط الاستمرار

- لا دمج أو نشر تلقائي من أعمال إعادة خط الأساس.
- لا تشغيل SQL المرفق ضد الإنتاج، ولا إدخال بيانات اختبار في قاعدة حقيقية.
- لا تعديل Push V2 أو PWA ضمن مهام Android إلا بمتطلب ومراجعة منفصلين.
- الحفاظ على الوحدات والهوية والعمل السابق، وإجراء التغييرات التالية في PRs صغيرة قابلة للمراجعة.
