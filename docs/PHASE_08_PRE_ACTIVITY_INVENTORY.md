# جرد المرحلة الثامنة — شاشة التجهيز قبل النشاط التعليمي

## الحالة

هذا المستند هو خط الأساس التنفيذي للمرحلة الثامنة، ومصدره فرع:

`official/phase-08-pre-activity-preparation`

لا يتضمن هذا الجرد نشرًا إلى Hostinger، ولا تشغيل SQL أو migrations على الإنتاج، ولا أي تعديل على Push V2 أو PWA أو service worker.

## الهدف الوظيفي

كل نشاط تعليمي في تطبيق الطالب يجب أن يمر عبر شاشة تجهيز Native موحدة قبل فتح واجهة الأسئلة. شاشة التجهيز تقرأ حالة الطالب الحقيقية من الخادم، وتعرض الأهلية والتكلفة والمحاولات، ثم تنشئ جلسة خادمية واحدة فقط عند ضغط «ابدأ النشاط».

فتح شاشة التجهيز وحده عملية قراءة ولا يخصم قلبًا أو جوهرة ولا يسجل محاولة.

## الوضع الذي تم العثور عليه في Android

- نقطة التطبيق الرئيسية موجودة في `app-student`.
- التنقل الداخلي للطالب أصبح typed داخل `feature-home` في المرحلة السابعة.
- وجهة خطوة الموجّه كانت تحمل معرف المادة والوحدة ونوع الإجراء، لكنها كانت تنتهي عند واجهة مادة انتقالية ولا تمر بمحرك تجهيز مستقل.
- لم تكن هناك وحدة Feature مستقلة مسؤولة عن دورة حياة تجهيز النشاط وإنشاء الجلسة.
- لم تكن هناك حالة محفوظة موحدة لمفتاح `Idempotency-Key` الخاص بمحاولة البدء.
- واجهات الاختبارات الخمسة ليست ضمن نطاق هذه المرحلة؛ المطلوب تثبيت عقد الانتقال إليها بعد إنشاء جلسة صحيحة.

## الوضع الذي تم العثور عليه في الخادم

- الخادم يملك مصادر قائمة للطالب والمادة والقلوب والجواهر والموجّه ضمن منصة الويب الحالية.
- بعض بيانات المحاولات والتكلفة النهائية مرتبطة بمحرك الاختبارات الذي لم يُنفذ بعد في تطبيق Android.
- لا يوجد قبل هذه المرحلة جدول مستقل لجلسات نشاط Android أو مسار موحد للمعاينة والبدء.
- هوية الطالب في مسارات Android الحالية مستخرجة من Bearer session.
- أي إضافة جديدة يجب ألا تكرر Push V2 أو جداول اشتراكات المتصفح.

## العقد المنفذ

### معاينة التجهيز

المسار:

`POST /api/v1/student/activity/preview`

عملية قراءة فقط تعيد:

- المادة والوحدة أو الدرس ونوع النشاط.
- حالة الأهلية والسبب.
- الاشتراك بحالة صريحة غير حاجبة في هذه المرحلة.
- القلوب والجواهر والتكلفة.
- المحاولات بحالة `available/reason` عند غياب المصدر المؤكد.
- عدد الأسئلة والمدة التقديرية عند توفرهما.
- جلسة سابقة قابلة للاستئناف.
- `version` و`generated_at`.

لا تنشئ هذه العملية جلسة ولا تخصم رصيدًا ولا تسجل محاولة.

### إنشاء جلسة النشاط

المسار:

`POST /api/v1/student/activity/start`

- يتطلب `Idempotency-Key` بطول وصيغة محددين.
- يستخرج الطالب من Bearer session فقط.
- يعيد معرف جلسة UUID ووجهة النشاط وحالة الخصم والرصيد.
- تكرار المفتاح نفسه مع الطلب نفسه يعيد الجلسة نفسها.
- استخدام المفتاح نفسه لطلب مختلف يعيد `409 idempotency_key_conflict`.
- لا يحدث خصم قلب أو جوهرة في هذه المرحلة؛ موضع الخصم النهائي سيُثبت مع محرك الاختبارات حتى لا ينشأ خصم مبكر أو مزدوج.
- يعاد التحقق من القلوب داخل transaction قبل إنشاء الجلسة.

### حسم نتيجة البدء غير المؤكدة

المسار:

`GET /api/v1/student/activity/start-status`

يستخدم المفتاح الأصلي لمعرفة هل أنشأ الخادم الجلسة بعد انقطاع الشبكة، دون إنشاء مفتاح أو محاولة جديدة.

## نموذج الجلسة

أضيف ملف Migration للمراجعة فقط:

`server-hostinger/database/20260724_api_activity_sessions.sql`

يتضمن:

- معرف جلسة عام غير قابل للتخمين.
- الطالب والمادة والوحدة والدرس.
- نوع النشاط ووضعه ومصدره وخطوة الموجّه.
- الحالة وتاريخ الانتهاء.
- بصمة الطلب وHash مفتاح منع التكرار.
- JSON الطلب والنتيجة المؤكدة.
- حقول الخصم المرتبطة بالجلسة.
- قيدًا فريدًا لكل طالب ومفتاح منع تكرار.

لم يتم تشغيل هذا الملف على Hostinger أو الإنتاج.

## التنفيذ في Android

أُنشئت الوحدة:

`feature-activity-preparation`

وتتضمن:

- `ActivityPreparationDestination` typed ومحدودة القيم.
- `ActivityPreparationRequest` مع تحقق محلي وبصمة SHA-256 مستقرة.
- DTOs داخل `core-network`.
- `ActivityPreparationRepository` مع تدوير Access Token عند الحاجة.
- `ActivityPreparationViewModel` لدورة المعاينة والبدء والاستعادة.
- مخزن DataStore صغير لمفتاح منع التكرار وبصمة الطلب.
- شاشة Compose عربية RTL غير مزدحمة.
- حالات التحميل والجاهزية والمنع والبدء والنتيجة غير المؤكدة وانتهاء الجلسة.
- تعطيل النقر المتكرر والانتقال مرة واحدة فقط بعد تأكيد الجلسة.

## الربط المنفذ

- زر خطوة الموجّه في الصفحة الرئيسية يمر الآن عبر `ActivityPreparationDestination`.
- عند نجاح إنشاء الجلسة ينتقل التطبيق إلى واجهة انتقالية آمنة تعرض أن الجلسة جُهزت.
- الواجهة الانتقالية لا تدّعي تنفيذ واجهات الأسئلة الخمسة قبل مرحلتها.
- التنقل الخارجي لا يتجاوز المصادقة أو شاشة التجهيز.
- مسارات المواد المستقبلية تستطيع إعادة استخدام الوجهة نفسها دون منطق موازٍ.

## قواعد منع التكرار

- إنشاء مفتاح واحد لكل نية بدء فعلية.
- الاحتفاظ بالمفتاح عبر دوران الشاشة وإعادة تركيب Compose وإعادة تشغيل التطبيق.
- تعطيل النقر المتكرر أثناء الطلب.
- عند انقطاع الشبكة بعد إرسال الطلب لا يُنشأ مفتاح جديد؛ يُستعلم أو يعاد الطلب بالمفتاح نفسه.
- الانتقال إلى النشاط مرة واحدة فقط بعد استلام جلسة مؤكدة.
- مسح المفتاح بعد تأكيد الانتقال أو تسجيل الخروج.

## البيانات المؤجلة صراحة

- واجهات الأسئلة الخمسة الكاملة.
- شاشة النتائج والمراجعة التفصيلية.
- اقتصاد الجواهر الكامل.
- مركز القلوب الكامل.
- عدد المحاولات المستخدم فعليًا حتى ربط محرك الاختبارات.
- عدد الأسئلة والمدة حين لا يعيدهما المصدر الحالي.

تعود هذه القيم بحالة صريحة أو `null` بدل اختراع بيانات.

## الاختبارات المضافة

- ثبات بصمة الطلب واختلافها باختلاف المحتوى.
- رفض المعرفات غير الصالحة قبل الشبكة.
- النقر المزدوج ينتج استدعاء بدء واحدًا بالمفتاح نفسه.
- المعاينة الخادمية لا تعدل جدول الجلسات.
- تكرار المفتاح يعيد الجلسة نفسها.
- تعارض المفتاح يعيد 409.
- الاستعلام بالمفتاح يعيد الجلسة المؤكدة.
- عدم حدوث خصم غير معتمد.
- منع نشاط يحتاج قلبًا عندما يكون الرصيد صفرًا.
- مطابقة fixtures الجديدة مع DTOs في Android.

## حدود الأمان المثبتة

- لا ثقة في القيم القادمة من Android مثل التكلفة أو الرصيد أو عدد المحاولات.
- لا اختيار لطالب من query أو body.
- لا تسجيل للتوكنات أو مفتاح منع التكرار الخام في قاعدة البيانات.
- لا Deep Link يتجاوز المصادقة وشاشة التجهيز.
- لا تعديل على Push V2 أو PWA أو service worker.
- لا نشر إلى Hostinger ولا تشغيل SQL أو migrations على الإنتاج.
